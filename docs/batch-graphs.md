## Runtime path

The [server step cap](development.md#native-streaming-server) applies to both prefill and decode. C++ defaults to four lanes and a zero step cap, which selects the legacy planner. With a positive cap, the ordinary planner rotates lane priority and assigns one row to each ready lane until the step budget runs out. It assigns remaining rows to MTP verification and then shares spare rows among lanes with prompt work. Plain `advance` admits at most one prompt row per lane. Chunked prefill uses tiles of up to 1,024 rows for text and 128 for media or MTP. [Tensor-core prefix reuse](prefix-cache.md#tensor-core-scheduling) uses a separate planner. [Batch options](../include/sglang/decoder_batch.h#L46)<!-- prefix: "struct Decod" --> · [Planner](../src/decoder_batch.cpp#L297)<!-- prefix: "StepPlan pla" -->

`--trace-batches` reports `target_rows` and `step_budget`. The total charges executed prompt rows, including the first-output row, one row per ordinary decode lane, and computed target verification rows for MTP. Prefix restores, score-only full hits, draft proposals, commit replays, vision encoding, and emitted IDs stay outside the total. `prefill_rows` lists configured slots in order, with at least four entries. `width` counts selected lanes, including lanes assigned no rows. `decode` counts executed decode lanes. K0 reports `peak_request_bytes` on active steps. [Step trace](../apps/server/batch_service.cpp#L377)<!-- prefix: "std::cerr \u003c\u003c" -->

Batch execution defaults to eager. Add `--batch-cuda-graphs` at [capacity two or higher](development.md#native-streaming-server) to enable replay for eligible steps. Both [prefix prefill policies](prefix-cache.md#tensor-core-scheduling) support eligible decode replay. A step that executes work for an [MTP lane](mtp.md#runtime-path) runs eagerly. In a mixed-depth batch, K0 peers can replay if they meet the replay conditions and the step assigns no work to any MTP lane. [Batch construction](../apps/server/batch_service.cpp#L167)<!-- prefix: "batch = std:" -->

The first eligible step per width runs eager. The next eligible step uses thread-local capture on the batch stream. Widths share batch-owned scratch. Capture keeps the device binding addresses fixed. Each launch uploads tokens, positions, KV page tables, KV and GDN pointers, and GQA score bindings. The graph runs embedding, decoder layers, and per-lane scoring. K0 lanes can mix greedy, sampled, and [constrained requests](text-serving.md#finite-choice-constraints) in one replay. Sampling and constrained selection run on the batch stream after replay. The batch maps winners back to logical slots and synchronizes before publishing or retiring lanes. With `--trace-batches`, each set bit in the 32-bit `graph_slots` mask identifies a replayed logical slot. Slot 31 uses bit 31. `width` counts all selected lanes. `request_bytes` includes request-owned scores and excludes batch scratch, CUDA graph allocations, and prefix cache storage. Active steps report prefill scratch as `workspace_bytes`. After the batch allocates sampling scratch, active steps also report `sampling_workspace_bytes`. The batch reuses this allocation across lanes and requests. A wide constraint adds a vocabulary mask and masked scores, for 552,256 bytes total. Each row uploads up to 16,384 bytes of IDs or a 31,040-byte mask. The lane keeps the host buffers live through the step. Sampling uses separate scratch. ## Resident memory admission

The HTTP batch service sets a fixed request memory limit at startup. It takes the GPU memory free after model and batch initialization and reserves up to 2 GiB for shared allocations. At admission, it checks both the remaining limit after active requests and current free GPU memory after the same reserve. The [row and lane caps](development.md#native-streaming-server) apply separately. C++ batch callers can opt in with `DecoderBatchOptions::resident_memory_limit` in bytes. The effective limit is the smaller of that value and the startup limit. [HTTP setup](../apps/server/batch_service.cpp#L167)<!-- prefix: "batch = std:" --> · [C++ option](../include/sglang/decoder_batch.h#L51)<!-- prefix: "std::optiona" --> · [Startup limit](../src/decoder_batch.cpp#L372)<!-- prefix: "if (options." --> · [Admission check](../src/decoder_batch.cpp#L458)<!-- prefix: "std::size_t " -->

Each positive-budget request reserves page-rounded KV for the encoded or expanded prompt length plus the output budget minus one. The charge includes target KV, GDN state, workspace allowances, and any MTP draft KV, verifier, or media position storage. The resident path initializes request storage at admission and prepares shared sampling and constraint buffers when needed. A zero-budget request skips the reservation. [Charge calculation](../src/decoder_resources.cpp#L314)<!-- prefix: "std::size_t " --> · [Initialization](../src/decoder_batch.cpp#L497)<!-- prefix: "if (lane.res" --> · [Zero budget](../src/decoder_batch.cpp#L534)<!-- prefix: "if (options." -->

The batch can reduce a [chat request's implicit output budget](chat-serving.md#sampling-defaults-and-output-budget) to fit the fixed memory limit. It retains an explicit budget. If the resulting request exceeds the fixed limit, HTTP returns 413. If it fits the fixed limit but exceeds available capacity, HTTP returns 503. A CUDA allocation failure during initialization also returns 503 if cleanup succeeds. The service retires the failed lane and keeps active peers. These responses carry JSON before streaming starts. C++ callers receive `DecoderCapacityError` and can inspect `retryable`. A terminal CUDA status or a failed drain disables the batch. The service fails current jobs and reports [worker failure](development.md#native-streaming-server). An affected stream that has started sends an SSE error and ends without `[DONE]`. ## Constraints and failure behavior

Each batch caches one executable per eligible packed decode width of two, three, or four. Sparse selections at those widths can replay inside a wider service. They reuse the executable with new bindings after request retirement. Steps that execute prefill or media work run eagerly. Packed decode outside widths two through four also runs eagerly. Wider decode submits one packed forward. Zero-budget lanes can finish outside the graph. A full prefix hit scores eagerly and stays out of the replay mask. Eligible decode peers can replay on that step. [Dispatch](../src/decoder_batch.cpp#L721)<!-- prefix: "const bool g" --> · [Full hit](../src/decoder_batch.cpp#L691)<!-- prefix: "if (lane.res" --> · [Zero-budget completion](../src/decoder_batch.cpp#L942)<!-- prefix: "result.finis" -->

Ordered fallback uses the slot's logits area at positions 0–5,119. At later positions that need ordered fallback, the first graph binding allocates scores for the request's page-rounded KV capacity. Each 128-position page needs 12,288 bytes for 24 FP32 scores per position. Capacity is at most 262,144 positions or 24 MiB of scores per lane. The kernels read the live position and score stride. The request keeps any allocated scores until retirement after stream completion. [Score binding](../src/decoder_batch.cpp#L634)<!-- prefix: "if (paged_de" --> · [Score allocation](../src/decoder_resources.cpp#L589)<!-- prefix: "ExactGqaWork" -->

If the first long-score allocation runs out of memory, the current step runs eager. That request remembers the failure and forces eager on later steps that need its long scores. Allocations already made for other lanes remain owned by those requests and can serve later replays. The executable remains available for other selections and recycled slots. Scratch OOM and recognized capture, instantiation, or synchronous launch rejections can disable one width. That fallback requires ended capture, a drained stream, and destroyed handles. Other widths remain eligible. A target-only execution error that escapes fallback disables the batch and fails current and subsequent requests. An invalid sampled or constrained selection retires only its lane. Cleanup retains resources while completion is uncertain. [Step recovery](../src/decoder_batch.cpp#L978)<!-- prefix: "if (!contain" -->

### Page-parallel GQA decode

Singleton K0 decode can use page-parallel attention with 1,536–2,560 visible tokens, including the current token. Both prefill policies share decode. Serial eager and serial graph calls can use this path when they select exact attention. Serial graph exact attention requires page-rounded KV capacity of at most 5,120 tokens. Device position selects the reduction inside the same two attention graph nodes. [Row dispatch](../src/decoder_forward.cpp#L178)<!-- prefix: "cudaError_t " --> · [Graph dispatch](../src/mxfp8_gqa.cu#L935)<!-- prefix: "cudaError_t " -->

An eager batch step can use the singleton path with one packed decode row, zero prefill rows, and zero work for MTP lanes. An independent full-prefix-hit score can run on that step. [Singleton dispatch](../src/decoder_batch.cpp#L724)<!-- prefix: "work[0].narr" -->

Each logical 128-token KV page produces an FP32 maximum, denominator, and value numerator per query head. The merge rescales both accumulators against the global maximum, divides, and rounds to BF16. This reduction order can change logits and greedy IDs. The path needs 495,360 bytes of the existing 496,640-byte logits allocation. Outside the window or with insufficient workspace, the exact path uses ordered replay. [Position window](../src/mxfp8_gqa.cu#L200)<!-- prefix: "__host__ __d" --> · [Page reduction](../src/mxfp8_gqa.cu#L237)<!-- prefix: "__device__ v" --> · [Workspace](../src/decoder_resources.cpp#L586)<!-- prefix: "return {rein" -->

A nonfinite visible score makes the merged denominator nonfinite. The merge checks the denominator and each channel numerator before writing output. The denominator must be finite and positive. Every numerator in the tile must be finite. If a check fails, the tile recomputes QK scores for that head and replays the tokens in order. The fallback stays in the same graph node. It follows the ordered operator's numerical rules, which can also produce nonfinite output. ### Packed paged GQA decode

At packed widths two through four, graph replay selects split attention per lane. The window covers 8,192 through 16,384 visible tokens, including the current token. Each layer appends all bound lanes' KV, runs attention, and gates the outputs on the batch stream. The executable reads live positions and skips split and merge work for lanes outside the window. Its ordered score and replay nodes handle those lanes. Eager forwards with two to four rows group in-window ordinary decode lanes after KV append. Other eager rows follow the existing row dispatch, including direct attention beyond inline score capacity. Prefill and MTP verification keep their existing attention paths. [Bounds](../include/sglang/decoder_cuda.cuh#L87)<!-- prefix: "inline const" --> · [Bound forward](../src/decoder_forward.cpp#L230)<!-- prefix: "void attend_" --> · [Eager forward](../src/decoder_forward.cpp#L253)<!-- prefix: "void attend_" --> · [Bound fallback](../src/mxfp8_gqa.cu#L766)<!-- prefix: "__global__ v" -->

The kernel distributes whole logical KV pages across 16 partitions. Each partition keeps the existing FP32 QK score order. It computes its maximum, exponential weight sum, and value numerator in FP32. Eight warps accumulate values with FMAs. The merge rescales both sums to the global maximum, divides in FP32, and rounds to BF16. The value reduction order can change logits. Each lane reuses 399,360 bytes of its 496,640-byte logits area for partials, with 16-byte alignment. In this window the graph skips the request-owned score binding. [Split](../src/mxfp8_gqa.cu#L553)<!-- prefix: "__global__ v" --> · [Merge](../src/mxfp8_gqa.cu#L653)<!-- prefix: "__global__ v" --> · [Scratch alias](../src/decoder_forward.cpp#L225)<!-- prefix: "PagedDecodeB" -->

A nonfinite visible score, visible V scale byte above 160, or invalid partial or merged result triggers FP64 replay for that query head. The merge requires finite numerators and BF16 outputs and a finite positive weight sum. Replay widens the decoded FP32 KV, processes the visible sequence in order, and rounds to BF16. Other heads keep their results. The captured sequence includes both FP64 head replay and ordered lane fallback. On the reserved B200, compare each width against eager with identical inputs under the same prefill policy. At equal packed widths, compare greedy IDs and complete BF16 vocabulary rows. Require bitwise parity when the attention route matches. Record the differences when the route changes. Test singleton transitions separately because changing width can change the GQA reduction order. Cross positions 127–129 and 5,119–5,121. Exercise inline and long strides in one replay. Change slot masks and request bindings at one width. Reject first-use score allocations at different packed lanes. Check retained bytes, eager continuation, and executable reuse after cancellation and slot reuse. Verify repeated bindings reuse existing allocations. Select a zero-budget lane alongside replaying lanes. After retirement, require zero request bytes.

Run the [streaming fixtures](development.md#streaming-verification) and [text checks](text-serving.md#verification) on both HTTP modes. Match IDs, finish reasons, and usage. ## Timing

Compare graph opt-in with batch eager on the same binary and prefill policy. To compare releases, enable batch graphs in both arms and match prefill policy. Freeze requests, arrivals, device, and warmups. Record cold capture separately and verify actual decode widths in a separate trace. Disable observers and trace output for timing. Frozen W3 and W6 begin decode above the inline score capacity.

A GPU4 decoder diagnostic compared `8b0da1a` with packed paged decode under the same tensor-core prefill policy. The median of 29 steady width-four graph steps fell from 102.799 to 27.890 ms. All 128 IDs matched. Timing excluded prefill, warmup, and graph capture. The [strict W3 timing](performance.md#native-concurrent-workloads) measures HTTP serving.

Before [frozen W1/W2 timing](performance.md#frozen-w1-and-w2-timing), repeat each native route for stable output IDs. If native builds diverge, compare full BF16 logit rows at the first differing step on their common history. Record the winner margin.

An earlier run before parallel MTP used one release binary on B200 GPU3 with driver 590.48.01. Both arms used `--max-active 4 --fp8-prefill exact`. The graph arm added `--batch-cuda-graphs`. MTP, observers, and tracing were off. The process order was eager, graph, graph, eager, with two warmups per process and 14 measured cohorts per arm. Each cohort sent four concurrent requests with 19–29 prompt tokens and returned 32 IDs per request. Maximum prompt plus output was 61 tokens. Timed SSE matched. Median output tokens/s increased from 110.83 to 113.65. Median cohort TPOT fell from 26.41 to 24.18 ms/token. The distributions overlapped, and the two eager process medians were 84.28 and 113.20 tokens/s. The historical record is `artifacts/batch-graph-acceptance/report.md`.
