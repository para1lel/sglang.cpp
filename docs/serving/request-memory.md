# Retired request allocations

A [resident-limited batch](../batch-graphs.md#resident-memory-admission) can keep device blocks after the target and any MTP draft finish using them. Later lanes in the same batch can reuse blocks of the same size. The reusable cache holds up to 768 MiB and 384 blocks on the batch's device. `request_device_allocation_bytes()` counts active request blocks and returns zero when all lanes retire, even if the batch retains blocks. Admission clears retained blocks when needed to preserve the shared reserve or fit the fixed limit. After a pressure trim, admission checks both limits again before it allocates request storage. After a CUDA out-of-memory status, the allocator can trim and retry once if the device has room above the shared reserve. The HTTP batch worker trims after five seconds waiting with no jobs. C++ callers can call `release_retired_allocations()`. Later requests may need fresh allocations. If releasing a block returns a nonterminal CUDA error, the batch logs it. A failed trim disables reuse of the retained set. A failed free during target or draft retirement keeps the completed result available for publication. Blocks with uncertain release status stay quarantined and count against the fixed request limit. Other reusable blocks remain subject to the cache limits. A terminal CUDA status or failed drain follows the [worker failure path](../batch-graphs.md#resident-memory-admission). Shutdown attempts to release blocks with confirmed ownership and completion while the CUDA context permits cleanup. The batch never retries an uncertain free. Unresolved allocations remain unavailable until CUDA tears down the owning context. An explicit trim reports a failure to restore the caller's CUDA device.
