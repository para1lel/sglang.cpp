# Retired request allocations

A [resident-limited batch](../batch-graphs.md#resident-memory-admission) can reuse same-size device blocks after the target and draft finish using them. With CUDA memory-pool support, the reuse cache holds up to 3 GiB and 1,024 blocks. A separate worker frees blocks on a nonblocking stream. Its queue accepts up to 1,024 outstanding blocks and normally up to 3 GiB. When the last checkpoint owner releases a detached block, the worker can accept it above the byte limit. If the queue declines it, the owner frees it on the per-thread stream and waits for completion. Without memory-pool support, the reuse cache holds up to 768 MiB and 384 blocks. `request_device_allocation_bytes()` counts active request storage. When CUDA reports that asynchronous release is unsupported, the owner frees the fenced allocation with `cudaFree`. Other CUDA errors propagate to the existing cleanup path. [Release fallback](../../include/sglang/runtime/backend/cuda_resources.h#L45)<!-- prefix: "inline cudaE" -->

Pending releases count against the fixed request limit until the release stream completes. Retired blocks that an exported checkpoint still owns also count against that limit. The recycling path cannot reuse them. Admission charges each block once as its ownership moves from the request to the exported view or release queue. Admission can drain pending releases and clear reusable blocks to preserve the shared reserve or fit the limit, then rechecks both before allocating. After CUDA allocation failure, the allocator can trim and retry once if the device has room above the shared reserve. The HTTP batch worker trims after five seconds waiting with no jobs. C++ callers can call `release_retired_allocations()`. The batch logs release errors, stops sending blocks to the release worker, and charges quarantined blocks against the fixed request limit until context teardown. Synchronous trim failures disable reuse of the affected cache. A terminal CUDA status follows the [worker failure path](../batch-graphs.md#resident-memory-admission) when the batch next checks the reclaimer. Each resident MTP slot reuses pinned host storage for up to five verifier winners. The batch keeps the buffer through its execution stream drain. Direct generation and a batch that cannot allocate the shared pinned buffer use the existing request-owned readback. [Winner buffer](../../src/decoder_verify.cpp#L562)<!-- prefix: "std::shared_" -->

Shutdown drains the batch stream before destroying request storage. The cache releases reusable blocks and drains work already queued. An exported checkpoint can keep the release worker alive after cache destruction. When the last owner releases the reclaimer, the worker finishes queued work and joins. Shutdown skips quarantined blocks.
