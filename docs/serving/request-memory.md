# Retired request allocations

A [resident-limited batch](../batch-graphs.md#resident-memory-admission) can reuse device blocks of the same size after the target and draft finish using them. With CUDA memory-pool support, the cache holds at most 3 GiB and 1,024 blocks. A separate queue with the same bounds releases completed blocks on a nonblocking stream. If both are full, any excess follows normal CUDA cleanup. Without memory-pool support, the cache holds at most 768 MiB and 384 blocks. `request_device_allocation_bytes()` counts active requests. Pending releases count against the fixed request limit until the release stream completes. Admission can drain pending releases and clear reusable blocks to preserve the shared reserve or fit the limit, then rechecks both before allocating. After CUDA allocation failure, the allocator can trim and retry once if the device has room above the shared reserve. The HTTP batch worker trims after five seconds waiting with no jobs. C++ callers can call `release_retired_allocations()`. The batch logs release errors, stops sending blocks to the release worker, and charges quarantined blocks against the fixed request limit until context teardown. Synchronous trim failures disable reuse of the affected cache. A terminal CUDA status follows the [worker failure path](../batch-graphs.md#resident-memory-admission) when the batch next checks the reclaimer.
