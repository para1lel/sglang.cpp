## Runtime path

Regular B200 batch replay supports one eligible direct decode lane. The first eligible step runs eagerly. The graph binds the live position, page table, KV, and score workspace for the selected request. At width one it requires inline score capacity through 5,120 visible tokens unless a shared score buffer is available. B200 does not use that buffer. Positive MTP uses a [separate verification graph policy](mtp.md#target-verification-graph). The standalone serial generator uses eager decode if its request can enter the split window. ### Generic SM100 singleton

The generic policy enables narrow attention for one direct batch decode lane. With sufficient workspace the page-parallel reader covers 1,536–2,560 visible tokens. Other rows with inline scores use ordered score and replay kernels. Eager rows beyond inline capacity use the scratch-free reader unless they qualify for shared scores. From 32,768 through 36,864 visible tokens, the generic batch can bind a single shared score buffer for eager or graph decode. Every GQA cache and the page table must cover the live rows. The batch allocates 3,538,944 bytes on first use for 24 FP32 scores per position. Each bind rounds its stride to a 128-token page. GQA layers and later requests reuse the buffer in stream order. ### Scratch-free ordered attention

Restored singleton prefill and allocation-limited prefill can reach the same reader as eager decode without score scratch. The public attention call keeps its tiny reader when the query end is below eight tokens. At eight or more it stages 32 keys for two query heads at a time. It applies the causal mask and accumulates values in token order. A standalone serial graph whose reserved KV exceeds inline score capacity uses the same tiled reader with a device position. Replay loads that position on each launch. ### Draft singleton reroute

Single scored lanes route through the batch entry; unscored draft seeding skips attention. On B200 a single lane now uses grouped online split GQA above 2,047 visible tokens; ineligible lanes keep the per-row routes. A geometry mismatch rejects the whole batch, and earlier rows may have already submitted. Target verification still selects winners from target scores and repairs draft state from verified rows. Approximate probabilities can change draft proposals. A paid W2 reroute measured 1,623.189917 to 1,454.878128 milliseconds against the pinned 1,420.734951; both native arms returned identical token streams, with one measured cohort each. The makespan delta includes changed verify-group composition. ## Split-KV target attention

B200 selects split-KV attention for eligible eager and bound text target rows from 2,048 through 262,144 visible tokens, including the current token. Bound kernels check the live position on device. Inside the window the reader decodes paged MXFP8 K/V to BF16 for Tensor Core attention, merges FP32 split partials, and rounds to BF16. Flagged heads use FP64 replay. Outside the window the target uses ordered attention. The split reductions can change scores and greedy IDs. ### Batched eager verification

The batched path requires vector attention, the full-context policy, and 2–20 rows inside the split window. It runs Q/K normalization and RoPE, KV append, split reads, and sigmoid gating in stream order. Each row keeps its workspace, KV page table, and causal position. Other groups run preprocessing, append, and gating per row. They can still group eligible reads. Bound replay uses its own dispatch. The [MTP verifier](mtp.md#runtime-path) owns acceptance and the committed KV prefix. TP2 vector-backend lanes below the split range batch their exact-scores and replay passes into one eager kernel pair. A side-effect-free eligibility check gates the route, and constrained or non-vector batches keep the per-row passes. Under the full-context policy, ordinary eager launches can group 10–20 rows. All inputs must satisfy Tensor Core alignment, and each row must average at most ten 64-token chunks per split. This route uses one shared-memory copy stage. It transposes QK across 16 keys and eight head slots (six active and two padded), then restores token order before masking and softmax. Other valid eager groups use at most five rows per launch. Narrow, singleton, and bound launches use two stages. Each row reserves scratch for up to 16 splits. ### Shared KV reads for long K4 packets

A full 20-row eager packet can share KV reads across four distinct cache and page-table identities. Each request contributes five consecutive zero-based positions within one 64-token chunk. Positions must be at least 32,768 and below 40,960. Each row needs readable KV, valid scratch, and Tensor Core alignment. One CTA per request, KV head, and split stages K/V and scales for its five rows. Each row masks its own tail and writes independent split partials. Other packets use ordinary split attention. ### Tensor Core reads across long K4 packets

The proposed W3 route selects eight complete five-row groups with distinct page tables and 12 query heads and two KV heads per TP2 rank. Each group's first zero-based position must be at least 8,191. Its fifth row must average at most ten 64-token chunks per split under the existing 20-row split packing rule. With at most 16 splits, the first position can reach 10,235 and the fifth can reach 10,239 (10,240 visible tokens). Groups can start at different positions and cross chunk or page boundaries. The route requires eager vector attention and the full-context split policy. Every row must be unconstrained, have no graph binding, and pass KV readability, alignment, and buffer checks. A wave that misses the W3 guard uses the existing selection rules below. [W3 guard](../include/sglang/text/gqa_verify_batch.h#L192)<!-- prefix: "inline bool " --> · [Split packing rule](../include/sglang/text/gqa_decode_split.cuh#L56)<!-- prefix: "inline bool " -->

For other shapes, the full-context eager Tensor Core verifier selects contiguous suffixes of one to five rows from positions 32,768 onward. Selected suffixes can cross a 64-token chunk or 128-token page boundary. Duplicate page tables in the wave prevent selection. Every selected row must be unconstrained and have readable KV and valid, aligned buffers. Earlier rows and ineligible requests run first in their original packets. The verifier then appends selected KV and submits one long reader and combine per GQA layer. [Sequence collection](../include/sglang/text/gqa_verify_batch.h#L159)<!-- prefix: "inline int c" --> · [Guard and suffix selection](../include/sglang/text/gqa_verify_batch.h#L208)<!-- prefix: "bool try_gqa" -->

One block per request, KV head, and split stages each 64-token chunk by TMA for up to five rows. Splits follow the first selected position and the final split extends through the newest row. Each row masks later keys. BF16 Tensor Core multiplies form FP32 scores. The value multiply accumulates the rounded BF16 weight and its rounded BF16 residual. This arithmetic can change scores relative to the ordinary split reader. The reader uses one expanded BF16 K slot and alternates between two expanded BF16 V slots. It refills a slot after the last QK or PV consumer of that slot finishes. The combine uses the reader's split count. Flagged heads still replay in FP64. ## Constraints and failure behavior

A clean shared-score OOM makes the generic batch remember the allocation failure. Long singleton steps use direct eager attention, while short replay remains eligible. Other allocation errors reach batch recovery. A recoverable graph rejection drains the stream, destroys its graph handles, and disables replay for that width. Eager decode can still use the retained score buffer. Batch cleanup drains the stream and destroys graphs before freeing it. [Allocation fallback](../src/runtime/backend/cuda_resources.cpp#L509)<!-- prefix: "ExactGqaWork" --> · [Graph recovery](../src/runtime/backend/cuda_resources.cpp#L568)<!-- prefix: "const auto f" --> · [Teardown](../src/runtime/backend/cuda_resources.cpp#L247)<!-- prefix: "CleanupError" -->

For the 20-row shared reader, a clean decline or a recognized optional setup or launch rejection returns that packet to the ordinary split route. A later packet can try again. A preexisting or distinct recorded CUDA error prevents fallback and remains recorded. The code clears only a recorded status matching the failed call and gives the returned status precedence on hard failure. [Rejection handling](../include/sglang/text/gqa/gqa_decode_reuse.cuh#L134)<!-- prefix: "std::optiona" -->

A clean device, shared-memory, or tensor-map setup decline sends the selected rows to the existing packet split dispatch. That dispatch reads their appended KV before gating. Pending errors and failed setup, reader, or combine calls propagate without retry. A recorded terminal CUDA error takes precedence over a nonterminal returned status. ### W3 shared-KV operator probe

Each case ran on one B200 with 12Q/2KV, BF16 queries, and MXFP8 KV, using eight warmups and 40 timed samples. At initial visible lengths 8,192, 8,704, and 9,216, median stream times for two 20-row split calls were 106.18, 116.45, and 115.71 µs. The eight-group TMA reader and combine took 69.44, 72.42, and 72.13 µs, respectively. The upper edge ran on a separate B200. At 10,236 visible tokens for the first row and 10,240 for the fifth, the split calls took 126.82 µs and the TMA route took 77.41 µs. Median host enqueue time rose in all four cases, from 8.93 to 10.85 µs at the upper edge.

Across 122,880 output values per case, the largest absolute difference between reader outputs was 0.000488. Against 3,072 independent FP64 values per case, the maximum absolute error was 0.000122 for TMA and 0.000153 for split. Evidence is in `artifacts/tp2-resume/w3-probe/run.log` and `artifacts/tp2-resume/w3-probe/edge.log`.

The focused route test passed at both position bounds, rejected the adjacent out-of-band cases and ineligible waves, and exercised the existing 32,768 suffix route. See `artifacts/tp2-resume/w3-probe/route-check.log`. [Route cases](../tests/decoder/long_decode_routes.cpp#L332)<!-- prefix: "void check_m" -->

The operator probe timed raw attention, including split and combine, on one rank. The [historical W3 campaign](serving/tp2.md#campaign-record) measured 4,918.77 ms native makespan on release `168fdb1a`. The candidate's makespan and serving correctness remain unverified.
